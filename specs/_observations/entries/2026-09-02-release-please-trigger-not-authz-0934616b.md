- 2026-09-02 [planwright] The release-please job gates on workflow_run conclusion == success and head_branch == main. Neither says who produced the triggering run. ci.yml has a bare pull_request trigger, so a fork PR from a branch named main (the default name, so the common case rather than an exotic one) completes ci in the base repo and fires this contents:write, pull-requests:write job. Two consequences beyond the one already accepted. First, an outsider controls when the privileged job runs and can force the standing release PR to be recreated after a maintainer deliberately closed it, which is D-3 cancellation surface. Second, conclusion is the FORK run verdict, so the header claim that a release is never proposed off a red main is not enforced: main can be red while a fork-main PR going green fires a proposal off main tip. release-hardening kickoff-brief declined the head_repository clause reasoning the default-branch pin was sufficient; that rationale covers only the must-not-execute-fork-code consequence, not these two.
