- 2026-09-09 [planwright] `core.hooksPath` in this clone keeps being rewritten from the tracked relative `githooks` to an ABSOLUTE path (`/home/<user>/dev/planwright/githooks`), twice in one working day, and no script in this repo writes that form: scripts/wire-githooks.sh and scripts/inception-scaffold.sh both set the relative value, lefthook is configured `no_auto_install: true` precisely so it never touches hooksPath, and the value lands in `.git/config` (local scope). So the writer is outside the repo's own tooling -- another session, a tool, or a hand-run command -- and it will keep happening until whatever does it is found. WHY IT MATTERS BEYOND TIDINESS: the relative form is what makes each worktree run ITS OWN branch's hooks, and githooks/commit-msg states that property in its header ("Hooks resolve through the relative core.hooksPath=githooks, so the hook running is always the one from the checked-out branch"). While the path is absolute every worktree runs the MAIN CHECKOUT's copy instead, so a branch that changes a hook is not screened by the hook it ships -- the documented property is silently false, which matters most for the branch whose whole purpose is changing that hook (the conventional-subject screen added 2026-09-08 is exactly such a change). DETECTION WORKS: `check:githooks` catches it on the next gate run and names the remedy, which is how it was found both times; the gap is that nothing prevents the rewrite or records who did it. Worth a cheap experiment before anything clever: set the value, note the time, and check it after each worktree add, each other session's command, and each mise task, to find the writer rather than continuing to re-run the remedy.
