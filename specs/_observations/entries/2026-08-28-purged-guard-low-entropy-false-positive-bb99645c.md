- 2026-08-28 [planwright] The purged-identifier guard (guard-coverage Task 3) false-positives catastrophically on low-entropy seed terms and fails closed, so a single common-token seed entry can brick the whole check gate repo-wide. On the first real seeding of PR #373, 5 seeded identifiers produced 78 matches across 22 tracked files (52 of them in specs/bootstrap/design.md + requirements.md + kickoff-brief.md, the rest scattered through scripts/, doctrine/, tests/, and observation entries) — far too many and too concentrated in origin-narrative prose to be genuine reintroductions. Root gap: check-purged-identifiers has no per-entry validation at seed time. seed-purged-identifiers.sh accepts any line that clears min-seeds/max-words, but never checks whether a candidate's hash already matches content in the current tracked tree — and a term that is already all over the tree cannot be 'kept out', it can only disarm nothing while failing every check run. The design acknowledged the identifiers are low-entropy names but shipped no guard against exactly this. Recommendations: (1) at seed time, reject (or warn-and-require-confirmation on) any candidate whose normalized hash already matches existing tracked content, naming the collision count so the operator sees the term is unusable before committing it; (2) consider scoping the tree scan to exclude historical/narrative surfaces (specs/bootstrap/*) or making the fail-closed on match advisory there; (3) until then, an operator with any low-entropy purged identifier (a plain repo name or handle) cannot wire this guard into check without a repo-wide false-positive storm. Found while seeding #373 to complete Task 3.
