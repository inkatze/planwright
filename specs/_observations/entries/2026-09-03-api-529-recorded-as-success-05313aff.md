- 2026-09-03 [planwright] A 529 Overloaded that kills a dispatched worker is recorded by the supervisor as a SUCCESSFUL run. Observed 2026-09-03: workers ai-6 and ai-7 (anchor-integrity tasks 6 and 7) both terminated with the assistant text "API Error: 529 Overloaded", produced zero commits, and their result frames are SELF-CONTRADICTORY: subtype=success alongside is_error=true, at 11 and 3 turns respectively. So the failure IS recorded, in is_error, while subtype simultaneously claims success. A caller reading subtype sees a completed run; one reading is_error sees a failure; nothing reconciles them. The tower's own stall detector read neither (it keyed on the event TYPE being 'result') and reported both as FINISHED. The API error arrives as ordinary assistant TEXT in the event stream, not as an error-typed event and not on stderr (both stderr logs were empty), so every liveness and completion check that keys on event type or exit status is blind to it: the tower classified both as FINISHED. This compounds streamjson-false-completion: there the signal was merely premature, here it actively mislabels a failure as a success, so a tower that trusts it frees the slot, marks the unit done, and moves on while the task has not started. The reconcile sweep cannot rescue it either, because the process exited cleanly and the branch has no commits to derive from, so the unit derives ready again only if the marker has expired. Candidates: have fleet-streamjson.sh scan terminal assistant text for the API-error shapes and set a nonzero result, or better, derive worker outcome from the unit contract (commits on the branch, PR opened) rather than from the process outcome, which is the same fix streamjson-false-completion argues for; and surface a zero-commit success as an anomaly rather than a completion, since a worker that finishes an execute-task with no commits has by definition not done the task.
