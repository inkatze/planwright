- 2026-07-28 [planwright] scripts/observation-carry.sh emits a PR body hard-wrapped at roughly 78 columns, and GitHub renders issue/PR bodies with hard line breaks enabled (a single newline becomes a literal br, unlike normal markdown paragraph flow). Every carry PR therefore renders as a narrow fixed-width ragged column instead of flowing to the panel width. Measured on PR #331: 12 body lines, 4 of them in the 60-85 column band, and the operator noticed the narrowness unprompted, comparing it unfavourably with PRs they author by hand. This is a SHIPPED-OUTPUT defect, not a one-off: the wrap is baked into the script, so it reproduces for every adopter on every carry, forever. Fix: stop hard-wrapping the generated body -- emit each paragraph as one long line and let the renderer wrap it; keep hard breaks only where they are semantically intended (list items, the carried-fragment filenames). Same class, different origin, in worker-authored PR bodies: PR #329 was 30 of 70 lines in that band (43 percent) because a dispatched worker wrapped its prose for a terminal; PRs #328 and #330 were only 7-8 percent and read normally. So the durable fix is the script; the worker-prose half is a dispatch-brief note (tell workers a PR body is rendered markdown, not terminal output). Cross-reference: this is invisible to every existing guard -- markdownlint runs on prose files, not on generated PR bodies, and no check inspects what a script emits to gh pr create.
