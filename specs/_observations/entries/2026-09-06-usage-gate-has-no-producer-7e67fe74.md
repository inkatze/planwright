- 2026-09-06 [planwright] fleet-usage-gate.sh has never once run its proactive path, and the reason is structural rather than a defect in the gate. Its capture verb PARSES a /usage render from stdin; nothing in the tree PRODUCES one. The only source of that render is the interactive TUI, and the tower is correctly forbidden from driving a TUI (the fleet doctrine allows capture-pane detection and buffer-paste relay, never send-keys impersonation). Verified empirically 2026-09-06: attempting to drive a THROWAWAY claude session in a scratch tmux window to generate the render was denied by the auto-mode classifier at tmux send-keys, which is the guard working as intended. The fleet home's usage/unavail-count sits at 2, so the gate is actively trying and failing, not idle. TRANSCRIPTS CANNOT SUBSTITUTE, which is worth stating because it is the obvious wrong answer: the rungs are PERCENTAGES of a window (session 50/70/85, weekly 60/75/85/95 per config/defaults.yml) and the JSONL session transcripts under ~/.claude/projects give absolute token counts, whose denominator is opaque and account-tier dependent. Feeding tokens to a percentage ladder would require re-deriving every threshold against a basis nobody publishes. THE ACTUAL CANDIDATE remains the one 2026-09-02-usage-signal-in-worker-stream already named: stream-json workers emit rate_limit_event frames carrying unifiedWindows with per-window UTILIZATION, which IS the percentage the gate wants, and persisting the newest such frame into the fleet home would give capture a real producer. Its limitation, newly relevant: only stream-json workers emit those frames. A fleet run on the SUBAGENT backend emits none at all, so that fix leaves the gate blind for subagent-backed runs -- the 2026-09-05/06 model-allocation run used subagents throughout and produced zero frames, while the newest frames on disk were two days old from dead workers. Any fix must therefore either cover both backends or declare the subagent rung explicitly unmeasured. Transcripts remain useful for a DIFFERENT question the gate does not ask: measured per-project consumption, which the account-wide window percentage explicitly cannot attribute (see the scope caveat in the same 2026-09-02 entry, where a tower throttled the fleet and killed a live worker on a number three unrelated sessions were driving).
