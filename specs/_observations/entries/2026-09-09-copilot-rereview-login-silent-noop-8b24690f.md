- 2026-09-09 [planwright] There is no reliable, observable way to trigger a GitHub Copilot re-review from the CLI, which matters because the standing ready-bar requires a review of the CURRENT head. Three forms, three different failures. `gh pr edit <n> --add-reviewer copilot-pull-request-reviewer` exits 0 and prints the PR URL while registering nothing (verified twice: reviewRequests stays empty). The REST form with that same login fails loudly instead: HTTP 422, "Reviews may only be requested from collaborators". `gh api -X POST repos/<owner>/<repo>/pulls/<n>/requested_reviewers -f 'reviewers[]=Copilot'` returns HTTP 200 with the PR object, and a review followed once about four minutes later -- but two later requests, one on the same PR after a new push and one on a freshly opened PR, produced nothing within twelve minutes of polling. THE LOAD-BEARING PART: reviewRequests reads empty immediately in ALL THREE cases, so nothing in the API distinguishes "queued" from "ignored", and a caller cannot tell success from failure. Whether the two silent failures were quota exhaustion, rate-limiting, or the request never registering is NOT established here and should not be assumed; quota is plausible, since it is the same bottleneck /panel-review exists to route around. Note also that the login Copilot REVIEWS under (copilot-pull-request-reviewer, which is what you must filter reviews by) is not a login you can REQUEST by. CONSEQUENCE FOR A TOWER: never block a handoff on a Copilot re-review landing. Poll with a bounded cap, then hand off stating plainly that checks are green and threads are clear but the newest Copilot review is at an older commit. Related trap: Copilot may return its findings as PR-level "suppressed comments" in the review body with no inline threads at all, so an unresolved-thread count of zero is not evidence that a review raised nothing.
