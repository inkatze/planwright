- 2026-09-09 [planwright] Re-requesting a GitHub Copilot PR review by the login that appears on its reviews silently does nothing. `gh pr edit <n> --add-reviewer copilot-pull-request-reviewer` exits 0 and prints the PR URL, but reviewRequests stays empty and no review is produced; the REST form with that same login fails loudly instead ("Reviews may only be requested from collaborators", HTTP 422). The login that works is `Copilot`: `gh api -X POST repos/<owner>/<repo>/pulls/<n>/requested_reviewers -f reviewers[]=Copilot` returns the PR object and a fresh review follows. So the name Copilot reviews UNDER (copilot-pull-request-reviewer, which is what you must filter reviews by) is not the name you REQUEST it by, and the ergonomic form of the request is the one that fails silently. WHY IT MATTERS: a tower that re-requests review after pushing a fix and then waits for a review at the new HEAD will wait forever with a green exit code and no error to notice, and the standing ready-bar (reviewed HEAD equals current HEAD) can never be met. Worth encoding wherever the review-request step lives rather than rediscovering it per session. Also note the review may land as PR-level "suppressed comments" in the review body with no inline threads at all, so an unresolved-thread count of zero is not evidence that a review raised nothing.
