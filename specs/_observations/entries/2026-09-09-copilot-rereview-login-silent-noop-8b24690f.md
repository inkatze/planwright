- 2026-09-09 [planwright] CORRECTED 2026-09-10 -- this entry previously claimed there was no reliable way to trigger a Copilot re-review from the CLI. That was wrong, and how it went wrong is the part worth keeping. THE MECHANISM EXISTS and roles/claude/files/commands/copilot-review.md already documented it: request with `gh pr edit <N> --add-reviewer @copilot` (the `@copilot` handle is special-cased by gh >= 2.88.0 and resolves internally), and verify through the issue timeline's `review_requested` events, `gh api repos/<owner>/<repo>/issues/<N>/timeline --jq '[.[] | select(.event=="review_requested")] | length'`. Verified working across roughly a dozen review rounds on three PRs, including the re-requests that carried #438 and #439 to a clean review and merge, so this is routine use rather than a single lucky call. The login forms genuinely do differ per API -- Copilot REVIEWS under `copilot-pull-request-reviewer`, REST `reviewers[]` needs the `[bot]`-suffixed form, and spelling the raw bot login to anything GraphQL-backed (including `gh pr edit --add-reviewer <login>`) fails with "Could not resolve user" -- so only the `@copilot` handle escapes that. THE ACTUAL TRAP, which the original entry misread as a broken mechanism: every requested-reviewer read-back HIDES BOT REVIEWERS. Both `reviewRequests` in GraphQL and `GET /repos/{owner}/{repo}/pulls/{n}/requested_reviewers` return empty even after a request that succeeds and produces a real review, so neither can distinguish success from a no-op. The skill records that an earlier revision of ITSELF trusted that same read-back and misdiagnosed a working request as "Copilot unavailable" -- the identical error, made twice, which is why the skill spells out the timeline check as the authoritative one. THE TRANSFERABLE LESSON: this was a CAPABILITY question ("can the tooling do X") settled by probing an API and generalising from an empty response, when it should have been settled by reading the skill that owns X. Probing is the right first move for behaviour and the wrong first move for capability, and a wrong capability finding recorded as an observation propagates into the repo and outlives the session that made it. Still true and worth keeping from the original entry: Copilot may return findings as PR-level "suppressed comments" in the review body with no inline threads at all, so an unresolved-thread count of zero is not evidence that a review raised nothing.
