- 2026-09-12 [planwright] The sanctioned tmux relay (orchestrate-relay.sh relay-command, load-buffer + paste-buffer -d) delivers a message into the worker CLI but cannot submit it, and whether it submits depends on the message length. A short single-line relay lands at an empty prompt and its trailing newline submits it; the worker picks it up. A long multi-line relay is turned by the CLI into a collapsed "[Pasted text #1 +N lines]" placeholder, which does NOT submit, so the message sits in the input box unread and invisible to capture-pane observation beyond that one placeholder line. Two relays stacked this way on one worker during a real run and the worker sat idle with both queued. Worse, once the input box holds multi-line content every SUBSEQUENT paste also fails to submit, including a short one-liner, so the box is unrecoverable from the tower side: clearing it needs a keypress the tower may not send, and fleet-cleanup.sh refuses to kill the window because the pane is still live. The worker had to be abandoned and the work relaunched into a fresh window. The workable rule found by experiment is: relay ONE SHORT LINE, and put any longer payload in a file for the worker to read. The tower may not press Enter (no send-keys impersonation, D-38), so there is no sanctioned completion of the relay path for anything longer than a line or two: the doctrine promises attributed relay as the coordination channel and the mechanism only delivers the short end of it. Either the relay contract should be documented as single-line-only, or the mechanism needs a submit path that is not impersonation (a worker-side inbox file the skill polls would do it).
