- 2026-09-07 [planwright] The pre-symlink LEGACY DIRECTORY break in scripts/fleet-state.sh try_acquire can still grant one home's advisory lock to two callers at once, and it is NOT fixed on the symlink-lock branch. Mechanism: the guard is `[ ! -L "$ta_lock" ]` then `[ -d ]` plus a staleness probe, and the removal `rm -rf "$ta_lock"` is separated from those by two forks. A peer that breaks the directory first, re-creates the lock as its own live SYMLINK, and is then overtaken by a breaker still holding the old probe result has its live link unlinked by that breaker's `rm -rf`; both then create and both believe they hold it. MEASURED 2026-09-07 by widening the probe-to-removal window with a 0.2s sleep and racing one prompt breaker against three delayed ones over a stale directory lock: 11 of 12 rounds granted twice (23 grants where 12 is correct). Under NATURAL timing the same harness produced 0 double grants, so this is invisible in ordinary runs, exactly like the sibling symlink race. THE SIBLING RACE IS FIXED, this one is not: the symlink stale break had the same shape (12/12 double grants widened) and was closed by reading the target being broken, renaming aside, then comparing what actually moved against what was probed and restoring it when they differ -- 0/12 after. The same rename-and-inspect treatment applied to the legacy path only moved the rate to 7 of 12 (and 2 of 12 on a second run, so high variance), which is why it was reverted rather than shipped: a partial mitigation in mutual-exclusion code buys false confidence, and the residual mechanism is not understood. Reachability is genuinely lower than the symlink race -- a legacy directory lock exists only on a home locked by the pre-symlink shape and never released, so it is a migration artifact -- but it is a real exclusion loss, not a theoretical one. Whoever takes it: start by explaining why rename-and-inspect closes the symlink path completely and this one only partly; that difference is the actual finding.
