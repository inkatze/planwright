Caveats to design around: the frames are per-worker and reflect the account window at that worker last spoke, so freshness varies and the newest across workers is the right read; a fleet with no live worker has no fresh frame, so the unavailable path must stay; and utilization is a fraction of an opaque window, so rung thresholds need calibrating against it rather than assuming a token budget. CRITICAL SCOPE CAVEAT, learned the hard way the same night: unifiedWindows is ACCOUNT-WIDE, not fleet-scoped. The operator had three other Claude sessions running concurrently with this fleet, so the tower's observed burn (62 to 92 percent over roughly an hour) conflated its own four workers with unrelated consumption it neither controlled nor could attribute. The tower throttled the fleet and terminated a live worker on that number. Any gate built on this signal MUST NOT treat utilization as fleet-attributable: it is a shared-resource reading, and reacting to it as though the fleet caused it produces exactly this failure, stopping fleet work to make room for consumption that continues regardless. Candidate designs: pair the account-wide window with the fleet's OWN measured spend (the per-worker usage totals already in each event stream) so the gate can report share-of-burn, and treat the account window as a ceiling to respect rather than a signal to attribute.
