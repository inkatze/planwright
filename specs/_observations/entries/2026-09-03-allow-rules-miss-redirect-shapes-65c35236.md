- 2026-09-03 [planwright] The worker allow-rule set matches command prefixes, so it approves a bare invocation and refuses the same invocation with output capture, which is the shape workers actually write. MEASURED 2026-09-03 with the auto-approve hook correctly installed: worker ai-6c ran 28 tool calls with 1 escalation, a 4 percent escalation rate and roughly 816 calls per hour, against 26 to 28 per hour for the same task without the hook. So the hook works; the residual is small but systematic. Of 10 escalated commands sampled across two hooked workers, 8 contained an output redirect, 5 a pipe, 4 an && chain, 1 a fish -c wrapper. Example refused while its bare form is allowed: `/bin/bash scripts/check-instructions.sh --closeout > /tmp/ci-instr.txt 2>&1; echo "EXIT=$?"`. Workers write that shape constantly because capturing to a file is how they read long output, and each refusal costs a full relay round trip (about a 5 minute stall in an attended tower, unbounded in an unattended one). Candidates: extend the allow set so an approved prefix stays approved when followed by output capture or a status echo; or have worker-command-guard.sh evaluate the leading command of a compound rather than the whole string, which is the more general fix but widens what a single rule sanctions and therefore needs its own blast-radius argument. Related: relay-latency-starves-workers, which measures the cost of the escalation path itself, and the dotfiles PR that moves the hook to user scope so it registers in every worktree.
