- 2026-09-03 [dotfiles] The two dotfiles CI jobs that fail on every run are exactly the two whose matrix entry brew-installs `mas`, and the correlation is complete rather than partial. In .github/workflows/test.yml the matrix sets brew_deps for each role; only `osx` (brew_deps: mas) and `upgrade` (brew_deps: "mas fish tmux") pull mas, and on PR #122 those are precisely the two jobs that did not pass, across two independent runs on 2026-09-03. Both report conclusion `cancelled` with the "Run osx tasks" step cancelled and the following steps skipped, against the job-level `timeout-minutes: 30`. A job killed by the timeout is recorded as cancelled rather than failed, and `gh pr checks` renders cancelled as "fail", which is what makes this read as flakiness from the PR view. It is not flaky in the sense of passing sometimes: `gh run rerun --failed` was tried twice and produced the same cancellation at the same step both times, so re-running is not a workaround and any PR touching this repo will sit un-green indefinitely. The diagnosis path that works is `gh api repos/<o>/<r>/actions/jobs/<id> --jq .conclusion` plus the per-step conclusions, since the PR-checks view collapses cancelled and failed into one word. Fix directions, none verified: raise timeout-minutes for those two roles, cache or pre-install mas rather than building it per run, or drop mas from the matrix if the roles do not actually exercise it. Worth noting for the tower generally: a check that is "failing" deserves one look at its job conclusion before a re-run, because cancelled-by-timeout and genuinely-failed need opposite responses and are indistinguishable from the summary.
