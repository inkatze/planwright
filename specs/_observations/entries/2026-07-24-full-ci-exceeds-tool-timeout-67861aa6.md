- 2026-07-24 [planwright] mise run check now takes ~630-805s wall clock (observed twice during merge-currency-guard Task 1: 629s and 805s), which exceeds the 600s ceiling on a single foreground Bash tool call. A worker that runs the mandatory full-CI step the obvious way gets its call cut off and moved to background, and the natural next move (yield and wait for the completion notification) is exactly the stream-json stall this fleet keeps hitting, where status reports "completed success" while the worker sits idle with work stranded. Workaround used here: nohup the run to a log file and poll synchronously with sleep loops, re-entering the poll after the poll itself times out. Worth making the ergonomic path safe rather than relying on each worker to rediscover it: e.g. a documented long-CI polling recipe in the execute-task CI step, a mise task that runs the suite detached and exposes a cheap status probe, or splitting check into a fast pre-PR tier plus a slower full tier. The two slowest single files (test-check-instructions.sh 629s, test-release-checklist.sh 450s) dominate and may themselves be worth a look. 2026-07-29 addendum, because the recommended workaround has a platform trap that bites silently: a worker whose plain `nohup ... &` run had already been killed by its own tool timeout reached for `setsid nohup /bin/bash -c '... run-tests.sh > log 2>&1; echo $? > done' &` to survive the next one, and `setsid` does not exist on macOS (`command -v setsid` is empty on Darwin; it is a util-linux binary). The launch therefore produced nothing at all, yet the command still printed its own "launched detached" echo and returned 0, because the failure was inside a backgrounded job whose status nobody checked. The worker then ran targeted tests, linted, and made four commits believing a full suite was in flight; the tower only caught it by checking `ls /tmp/wider-suite.*` and `pgrep -f run-tests` from outside and finding neither the log nor the exit-code marker, which is decisive because the inner redirect would have created the log the instant the job started and the `echo $?` would have created the marker on any exit. Two durable lessons: a detached launch must be verified to have STARTED (log file exists and is growing, pgrep non-zero) before anything downstream may assume it is running, since an unverified launch is indistinguishable from no launch; and a relaunch recipe that begins `rm -f` the previous log destroys the partial evidence that would otherwise show how far the earlier attempt got. If a documented long-CI recipe lands per the note above, it should use a portable detachment form rather than `setsid`, and should end by asserting the log exists rather than by echoing that it launched.
