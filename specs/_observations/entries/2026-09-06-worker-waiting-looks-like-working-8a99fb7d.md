- 2026-09-06 [planwright] A worker blocked on a condition that has already resolved, or can never resolve, is indistinguishable from a worker making progress. Two instances in one session, 2026-09-06, both self-inflicted by the worker's own polling rather than by anything external. (1) A review worker started a background test suite, then stopped each turn to "wait for the completion notification" — the wait was itself the blocker, since the pending edit it was deferring was a one-line comment change it had decided not to make while another process read the file. It emitted THREE reports whose text was word-for-word identical. The only signal that anything was wrong was noticing that identity; every individual report read as reasonable in-progress status. It was unblocked only by an explicit instruction to abandon the background run, edit anyway, and run the gate in the foreground. (2) A second worker left an orphaned shell 'until' waiter blocking on a suite whose condition was already true; the waiter was eventually SIGTERMed and surfaced as an exit-144 "failure" notification for a run that had actually completed cleanly, so the visible signal was not merely absent but actively misleading. THE GENERAL SHAPE: liveness checks answer "is the process alive", not "is the process advancing". planwright's own stuck detector classifies a worker as working partly from a busy marker in the pane footer (a running-turn spinner), and a spinner turns identically whether the worker is progressing or blocked on a condition that will never fire. This is the other half of the problem the is_error work addresses: that one covers a worker that DIED and was read as finished; this covers a worker that is ALIVE and read as working. Candidate signals worth considering, none implemented: successive worker reports that are byte-identical are strong evidence of a stall rather than progress; a worker whose journal has not gained an entry across N boundaries while its process lives; and treating a self-started background wait as a distinct state from work, since in both instances here the worker was waiting on ITSELF. Worth noting for whoever takes it that a fix must not simply shorten timeouts — both workers would have passed any liveness probe, and instance (2) shows a timeout firing on a healthy condition produces a false failure report, which is its own harm.
