- 2026-08-18 [planwright] Recurring guard-authoring hazard, now hit twice in guard-coverage: a matching surface that the UPSTREAM system treats case-insensitively silently defeats a case-sensitive guard. Task 1 found it in git (`core.hooksPath` config keys are case-insensitive, so a case-sensitive deny glob is evadable by casing) and recorded arbitrary casings as a residual. Task 4 found the same shape in GitHub Actions (expression contexts AND secret names are case-insensitive: `${{ SECRETS.foo }}`, `${{ SeCRetS.Baz }}` all resolve), where a case-sensitive scan for `secrets.` let a stored secret through a pull_request-reachable job. Both were reproduced before fixing. Candidate for a guard-authoring rule in the doctrine: when a guard matches identifiers owned by an external system, establish that system's case semantics FIRST, and when it is case-insensitive, normalize both the match and any exemption (an exemption left case-sensitive becomes a false-positive source, which is how the GITHUB_TOKEN carve-out behaved before the fix).
