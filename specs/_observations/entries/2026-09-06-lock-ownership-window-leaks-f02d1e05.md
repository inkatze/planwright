- 2026-09-06 [repo] fleet-state.sh leaks the shared fleet lock when a signal lands between taking it and recording ownership. try_acquire mkdirs the lockdir and returns 0; HOLD_LOCK=1 is set by the CALLER, spin_acquire, after the return. A TERM in that window runs trap exit 143 then the EXIT trap, and release_lock sees HOLD_LOCK=0 so it declines to rmdir a lock this process really holds. The leaked lock then wedges every later fleet writer until the stale break, which is the exact outcome the surrounding comment says the discipline exists to prevent, and test-fleet-registration e8 asserts against in its own words. Reproduced 2026-09-06 under deliberate CPU contention (24 busy workers on 12 cores): e8 failed and the following registration hung until a 300s timeout on the leaked lock; the same file passed 3 of 3 in isolation, so isolation is not evidence here. try_acquire is deliberately not the place to record ownership because the exposed one-shot lock command hands the lock to a later process, so the fix has to close the window without moving it there.
