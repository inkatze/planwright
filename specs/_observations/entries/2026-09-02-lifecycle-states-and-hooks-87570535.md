- 2026-09-02 [planwright] Operator request 2026-09-02: give the development/execution process named STATES with arbitrary operator-attachable hooks at each, where a hook may be a shell command or a skill invocation. Today the pipeline has many implicit transition points but only Claude Code process hooks (PreToolUse, PostToolUse, SessionStart, etc, in hooks/hooks.json) which key on TOOL events, not on pipeline semantics. There is no way to say "before every dispatch, run X" or "after a unit converges but before its PR opens, run /panel-review" without editing skill bodies. The review_sequence knob is the one existing example of a pipeline-semantic extension point, and it is narrow by construction: it admits only planwright-owned skills whose argument-hint declares --nested, which is why /panel-review and /copilot-review cannot be wired into it and had to be run as manual tower-level steps this session. That narrowness is the concrete evidence the general mechanism is missing. Candidate states, drawn from what this session actually needed a seam at: spec-drafted, kickoff-signed-off, unit-selected, pre-dispatch, post-dispatch, implementation-green, pre-review-sequence, post-review-sequence, pre-PR, post-PR, pre-ready-flip, post-merge, unit-halted, tower-idle. Design questions the spec must settle: whether a hook can veto the transition or only observe (a veto turns hooks into guards and inherits the deny-emitting risk model ready-guard.sh documents); how a hook is passed context (the unit, spec, branch, PR number, findings) without coupling it to internals; failure posture per hook (fail-closed vs degrade, likely declared per hook rather than globally); ordering and composition when several attach to one state; and how this layers with the existing overlay precedence so an adopter can add hooks without editing planwright core.
