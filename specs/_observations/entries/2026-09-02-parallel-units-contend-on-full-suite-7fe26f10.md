- 2026-09-02 [planwright] max_parallel_units (default 3) governs how many units dispatch concurrently but nothing governs what those units then run locally. Each /execute-task worker runs the full `mise run check` at its convergence gate, so N in-flight units means N concurrent full test suites on one machine, each slowing the others. Observed 2026-09-02 in a --fleet wave of three units: two workers entered `mise run check` within minutes of each other and a third began polling with a 55-iteration/10s wait loop; one worker independently started probing `pgrep -fc "fish -c mise run check"` to explain its own slowness, which is the worker noticing fleet-level contention it has no way to see or coordinate around. The bound is a dispatch-admission control, not a resource control, and the two are being conflated. Candidates: a fleet-level advisory lock or token around the full-suite step so suites serialize while implementation stays parallel; or a per-unit fast-check (only the suites the diff touches) at the convergence gate with the full suite reserved for CI, which already runs it on the PR anyway. The second is likely better: the full local suite largely duplicates what the PR check job re-runs.
