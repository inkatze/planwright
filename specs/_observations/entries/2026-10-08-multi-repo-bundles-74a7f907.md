- 2026-10-08 [planwright] Multi-repo bundles: a spec root held in a separate repo (custom-spec-location) now serves several work repos, but a bundle whose tasks target different repos cannot be executed. Task blocks name no repository, and orchestrate-state.sh derives state from the single repo resolve-work-repo.sh picks (the launch repo), so /execute-task step 8 halts on a dependency merged in another repo and plain /orchestrate would dispatch every task into the launch repo's worktree. Two signed bundles in one holder hit this across three work repos plus the holder: some dependency edges cross repos (a backend publish, frontend build, backend register sequence; a frontend task depending on backend and service tasks), some blocks span two or three repos in one task, and some tasks live in the holder itself or in no repo (tracker edits). Splitting per repo would lose exactly the cross-repo edges, since there is no cross-bundle dependency syntax. Seed for a custom-spec-location extension: an optional per-task repository field resolved to a local checkout through machine-local config (never a path in the bundle); state derived from the union of the bundle's repos; dependencies satisfied across repos; /orchestrate dispatching each unit into its own repo; a defined home for holder-only and no-repo tasks; mixed-repo blocks either rejected by the validator (forcing a split) or given an explicit multi-repo unit form.
