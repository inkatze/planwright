- 2026-09-06 [planwright] tests/test-fleet-registration.sh case e8 (an interrupted registration releases the shared fleet lock) is load-flaky with a concrete mechanism, not an unexplained flake: the case backgrounds a register, sleeps a FIXED 0.05s, then sends TERM. Under machine load the child may not have armed its cleanup trap within that window, so the TERM lands with the lock dir created and no handler to remove it, and the case fails. Measured: run 8-way concurrent it fails about 3 of 8, and running the SAME 8-way against origin/main dc0442a in a detached worktree AT THE SAME TIME gives the same 3 of 8 at base, so the rate is a property of load rather than of any branch. The earlier archive-based comparison is not valid for this suite: git archive yields a non-git tree and case b1 (owner tokens) then fails 8 of 8 for an unrelated reason. Follow-up: replace the fixed sleep with a poll for the child's readiness (the lock dir appearing, or a readiness marker the register writes) before signalling, so the case stops encoding an assumption about process start latency.
