- 2026-09-20 [planwright] scripts/observation-carry.sh dedupes candidate fragments by path, so a fragment already on the chore branch is skipped even when its content has changed on the tower branch, and the run reports `carry noop` / `stranded 0` / exit 0. Reproduced: fragment 9d3f21c4 was carried to the chore branch at 1043 bytes, then revised on the tower branch to 1271 bytes (a suspicion sharpened into a two-run reproduction) and committed; the next carry reported noop with stranded 0, and `git show origin/planwright/chore/observations:<path>` still returned the 1043-byte text, so the revision reached nothing and nothing said so. This is the case the script's own documented invariant rules out: "Nothing is stranded SILENTLY: a degrade names the stranded observations and exits non-zero" (REQ-K1.6, REQ-K1.7). Path-identity dedupe is the right call for the idempotency it is written for (a repeat run must not carry twice or open a second PR), but it silently conflates "already carried" with "already carried in this form". A tower that corrects an observation before the chore PR merges loses the correction, which is the common case, since observations get sharpened as their reproduction firms up. Worth deduping on blob identity rather than path, and treating a path match with a different blob as a fragment to carry (a new commit on the chore branch, which the no-force-push floor already allows) or at minimum as a named, non-zero-exit strand. Distinct from the stranded miscount in obs:9d3f21c4, which concerns a successful carry reporting a phantom strand; this one concerns a real strand reported as none.
