- 2026-09-03 [planwright] A stream-json persistent worker emits a `result` frame at the end of each TURN, not at the end of its run, and the process stays alive to accept more input. A tower that reads a result frame as "this worker is done" is wrong, and the error is not cosmetic. On 2026-09-03 the tower read a FINISHED line for dotfiles-comments, concluded the single dotfiles working tree was free, and launched a second worker (review-dotfiles) into it while the first was mid-flight with an uncommitted edit to roles/claude/files/CLAUDE.md and an in-progress panel-review iteration loop. Two workers in one plain checkout on different branches is the collision that has already caused data loss in this run. It was caught within a minute and the second worker was stopped before it touched anything, so nothing was lost, but only because the first worker happened to escalate a permission and reveal it was still running. The same misread had already occurred earlier in the run with coc-5b, which emitted `subtype=success` at 95 turns with a clean tree, zero pushed commits and no PR, and then carried on working. Liveness is the process, not the frame: `kill -0 $(cat worker.pid)` is the test, and a worker with pending journal entries is by definition still running. This matters most for repos without worktree-per-unit isolation, where the working tree is the contended resource: in planwright each unit gets its own worktree and a spurious relaunch is merely wasteful, while in dotfiles it is destructive.
