- 2026-07-30 [planwright] release-please can regenerate an entire changelog into a merge-ready PR, and this repo has a structural race that reaches that state on every release. Observed 2026-07-30: minutes after v0.33.0 was published, PR #339 "chore: release 0.34.0" appeared proposing a bogus minor bump with 124 changelog entries re-listing commits that shipped in earlier releases (#159, #197, #307, #312, #314, #316). The run log is decisive -- `looking for tagName: v0.33.0` at 19:18:59, then `Needed bootstrapping, found configured bootstrapSha 71ea089f...` and `No latest release found for path: ., component: , but a previous version (0.33.0) was specified in the manifest` -- while the signed tag was published at 19:19:02, three seconds later. TWO separate defects are in play, and fixing only the first leaves a landmine. Defect 1, the trigger: the release-please workflow fires on `workflow_run` of `ci` completing on main, and for a release commit that interval is exactly when the tag deliberately does not exist, because CI never tags (REQ-C1.3) and publishing is the human-gated signed step. Every release passes through that window; this was not bad luck. Defect 2, the blast radius, is the more dangerous one: when release-please cannot see the latest release it silently falls back to bootstrapSha and regenerates from near the start of history rather than failing loudly, so ANY cause of "cannot see latest release" -- an API blip, a rate limit, a permissions hiccup, a deleted tag -- yields a plausible-looking merge-ready PR whose diff a tired reviewer could accept. A repo 30-plus releases in should not be able to bootstrap at all. Fixes, cheapest first: (1) gate the workflow on scripts/release-window-check.sh, which already exits 1 precisely when an untagged window is open and whose message already says no further merge should land until the signed tag is published, so release-please skips while a release is pending publish and runs normally once the tag exists; (2) add a cause-agnostic sanity check that fails when a release PR adds changelog entries older than the latest tag -- the one least worth skipping, since it catches a bootstrapped proposal regardless of how release-please got confused, and it is the same shape as the fixture-count floors in tests/test-permission-matcher.sh; (3) INVESTIGATE removing bootstrap-sha from release-please-config.json, since it exists only for a first release and its absence should make the failure loud rather than generative -- marked investigate because release-please 17.6.0 behaviour with the key absent was not verified. Interim operational rule: after publishing any signed tag, check whether a bootstrapped release PR appeared and close it, since this workflow documents the release PR as its own cancellation surface. #339 was closed with the diagnosis attached; v0.33.0 itself verified clean -- good signature, tag on 294e773, release-window-check reporting the window closed.
