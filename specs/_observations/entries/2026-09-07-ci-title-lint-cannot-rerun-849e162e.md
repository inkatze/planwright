- 2026-09-07 [planwright] The CI workflow lints the PR TITLE but can never re-evaluate it when the title changes. .github/workflows/ci.yml declares a bare 'pull_request:' with no types, so it fires on the default opened/synchronize/reopened and NOT on edited. The title check runs as a distinct step after the commit-subject lint, reading PR_TITLE from the event payload. Consequences observed 2026-09-07 on PR 414: the PR failed CI solely because its title lacked a conventional-commit prefix, and the failure was misread for hours as a test hang because the job's tail shows orphan-process cleanup rather than the failing assertion. Correcting the title changed nothing, because no event fires on edited; and 'gh run rerun' does not help either, since a re-run replays the ORIGINAL event payload and therefore re-reads the stale title. The only ways to re-evaluate are to push a commit (a spurious one, if the title was the only defect) or to close and reopen the PR, which is what was done. Candidate fix: add types: [opened, synchronize, reopened, edited] to the pull_request trigger, so a title correction is verifiable by the same gate that rejected it. Worth checking whether the concurrency group (ci-${{ github.ref }}, cancel-in-progress) makes an edited-triggered run cancel an in-flight synchronize run for the same ref, which would be a mild regression to weigh against the fix. Second-order note: a gate that can reject an input it cannot re-check is a one-way door, and the repo already carries a class of guards that pass when they should fail; this is the mirror case, a guard that fails with no path back to green.
