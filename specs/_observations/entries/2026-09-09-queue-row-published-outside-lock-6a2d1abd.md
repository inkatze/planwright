- 2026-09-09 [planwright] An answered request could stay in the operator decision queue, because the queue row is a projection of journal state that both writers derived and published OUTSIDE the lock protecting that state. In fleet-streamjson.sh, handle_line appended the receipt under journal_lock, unlocked, then published the queue item; cmd_answer marked the row answered under the lock, unlocked, then cleared the queue. Interleave them and handle_line reads pending, answer flips to answered and clears the row, and handle_line's write lands on top -- a lost update that re-posts a decision the operator already made. Operator-visible consequence: the queue shows a decision that has been made, and answering it again hits the already-answered/undeliverable refusal, which is exactly the "no request may pend permanently unanswerable" property c12 exists to protect. HOW IT WAS FOUND, which is the transferable part: test-fleet-streamjson.sh c12 "queue should be clear after the answer" had been failing the full parallel gate while passing in isolation, and was written off as a load flake more than once. The assertion asserted a value without reporting it. Making it print what it actually saw diagnosed the bug in two runs: it killed the first hypothesis immediately (the count was 1, not the empty string a suppressed queue subcommand would give) and then handed over the mechanism, because the dump showed the journal reading answered at T and the attention store still reading awaiting-input at T+1 -- a store write that postdated the answer it contradicted. A bare boolean assertion on a racy invariant costs more in repeated archaeology than the dump costs to write. FIRST FIX WAS WRONG and the wrongness is instructive: re-deriving from the journal instead of publishing the captured id (attention_settled rather than attention_upsert) narrowed the window without closing it -- the store timestamp moved from one second after the answer to equal to it -- because the read and the write were still not atomic with respect to the other writer. Deriving is necessary (the row is meant to carry the OLDEST still-pending request, not the newest) but not sufficient; the derive-and-publish has to happen under the lock. Two things make holding it safe: journal_lock is a non-reentrant mkdir lock and nothing reachable from attention_settled re-takes it (journal_oldest_pending is an unlocked read), and fleet-attention.sh contains no reference back into fleet-streamjson.sh, so the journal-then-attention ordering cannot invert. THE THIRD WRITER: cmd_alarm_scan carried the same shape and was initially left alone as needing its own thought, which was wrong -- a sweep that reads the journal unlocked and upserts afterwards recreates this exact row whenever it overlaps an answer, so the fix was incomplete without it. It now re-reads the whole row and publishes under ONE lock held across both. Taking the lock twice -- read, unlock, decide, relock, publish -- was tried first and is worth recording as a wrong answer that looks right: it puts the entire decision outside any lock, so an answer settling the request in that gap is overwritten by the publish, which is the row this whole entry is about, reintroduced by the fix for a different finding. The whole ROW, not just its state: a request can be answered and then re-opened with a fresh received epoch while the scan waits for the lock, and a state-only re-check sees pending again and escalates against the age the first scan measured, marking a request overdue before it has had its threshold. A lock the scan cannot take ends that worker for the pass rather than the single request, because skipping per-request sends every remaining row of a busy worker through the same retry budget. OUTCOME: moving derive-and-publish inside the journal lock at all sites took the streamjson suite from 4/4 failures (including on main) to 4/4 passes across clean sequential gate runs. Passing runs narrow a race rather than disprove one, so this is evidence and not proof. Two things safe about holding the lock across the shell-out: journal_lock is a non-reentrant mkdir lock and nothing reachable from attention_settled re-takes it, and fleet-attention.sh has zero references back into fleet-streamjson.sh, so journal-then-attention cannot invert.
