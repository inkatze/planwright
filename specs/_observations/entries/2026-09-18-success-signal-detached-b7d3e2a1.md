- 2026-09-18 [planwright] Seven times in one review evening a signal read as success while not being attached to the thing it claimed to report, through six different mechanisms, and every fix was made at its own site. The list is the argument, because any one of them looks like a slip: (1) the awk store pass reports a load failure as a `fail` record and exits 0, so `knock` rendered the failure as a knock line and `counts` printed a clean zero reading after it, END having run regardless; (2) `$(f "$(run capture ...)" 2)` discards the inner command's exit behind the outer substitution; (3) `cmd | tail -30; echo "exit: $?"` reports tail's status, so a tooling script declared ten linters green at once; (4) `[ "$(... | grep -c .)" = 1 ]` asserting exactly one line while counting non-empty lines; (5) a panel-backend lens table with nine `none` rows whose reasons were compliments, exit 0 throughout, which reads as a clean slice and was a blank-out; (6) `until ! pgrep -f "mise run check"` never firing because the waiting shell's own argv carries the pattern; (7) a `[ -f ]` store selection on the lock-free read path that trusted a symlink, a check that appears to verify and does not. The common shape is a measurement whose success channel is a different process, a different line, or a different question than the one the caller acts on, and the codebase's own doctrine already names the family (a guard that passes because its measurement went missing) without a mechanical check behind it. Two guards suggest themselves and neither is built here: a `check:swallowed` pass over the shell tree for the syntactic forms that detach an exit status (`$( ... | ... )` feeding a test, `; echo $?` after a pipeline, `$?` read after anything but the command it belongs to, `grep -c` compared against a count meant as a line count), and an awk convention that a `fail` record must be paired with a nonzero `exit` so a caller that forgets to scan the output still sees the status. The review-checklist form is cheaper still: one line under the error-handling lens asking, of every success signal the change reads, which process produced it and whether that process is the one whose failure matters.
