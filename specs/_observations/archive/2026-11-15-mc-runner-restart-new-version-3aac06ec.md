- 2026-11-15 [planwright] (hub, three sessions during the 0.76.1 upgrade) Restarting a mission-control runner (scripts/mc-watch.sh run) onto a new planwright version has no supported path. (1) mc-watch.sh stop does not stop a live runner: by its own --help it stops armed watchers and, with a runner live, prints busy and exits 1 ("stop the runner first"), and no verb stops the runner itself, so an upgrade signals processes by hand; on the hub it looked like a cross-version no-op (0.76.1's stop left a 0.75.2 runner running). (2) Signals do not end the runner cleanly: it is a parent run process (ppid 1) with a child run that owns the loop slots; a TERM on the parent is deferred while it waits on the child, the parent re-forks the child and slots if they are killed first, and a TERM on the run pid alone left its loop processes orphaned and running (spec-pipeline). What worked on mc-fixes: TERM the child run and all its loop pids together, then the parent exits. (3) A restarted runner inherits the launching session's CLAUDE_PLUGIN_ROOT and PLANWRIGHT_ROOT, so one started from a session that loaded an older plugin runs with the old roots even from the new version's script path (seen on the hub, dotfiles and mc-fixes); what worked was exporting both roots to the new install root before setsid -f <new root>/scripts/mc-watch.sh run --program <p>. (4) Killing loop slots raises a burst of watcher-failing events per slot until the new runner re-arms them. Recommended fixes: a mc-watch.sh stop-runner (or stop --runner) verb that ends the parent, the child and every loop slot of a program's runner whatever version started it, matching on the program and the runner's recorded pids rather than the script path; the run process ending its loops on TERM; and run resolving its own root from its script path instead of trusting inherited CLAUDE_PLUGIN_ROOT and PLANWRIGHT_ROOT (or refusing to start when they name a different version).
