- 2026-07-29 [planwright] A tower-side relay written to a stream-json worker MUST be newline-terminated, or it kills the worker. On 2026-07-29 the 0.32.1 tower relayed the same guidance to two live workers using python `open(path,"w").write(json.dumps(obj))` -- no trailing newline -- then `cat file > in.fifo`. The unterminated object concatenated with the very next line the supervisor wrote (a control_response for an in-flight permission answer), producing two JSON objects on one physical line; each worker`s stream-json input parser raised `Error parsing streaming input line: ... SyntaxError: JSON Parse error` and the process exited. Both workers died within seconds of each other, mid-unit, with gauntlets nearly complete: guard-coverage task-1 at 7 commits and a clean tree, merge-currency-guard task-2 at 5 commits plus 3 uncommitted files carrying failing P1 fixtures it was actively debugging. Nothing was lost (commits and worktrees survive a worker death) but neither had pushed, so a tower that had stopped watching would have read this as two silent stalls. Three things make this worth pinning. (1) The failure is invisible from the fleet oracle: worker.pid and supervisor.pid are simply emptied, so `status` reports nothing useful and only stderr.log names the cause -- diagnosis requires reading stderr.log, not polling status. (2) It is timing-dependent, which is why earlier relays in the same session succeeded: every prior relay used python `print(json.dumps(...))`, which appends the newline, and the corruption only manifests when the supervisor writes another line before the next newline arrives -- so an unterminated relay can appear to work when the worker happens to be idle. (3) It scales with relay frequency and fleet width, exactly like the shared-/tmp-filename hazard: a tower that steers more workers more often is likelier to interleave a write. Mitigations, cheapest first: always terminate with an explicit newline and assert it (`assert line.endswith("}\n")`) plus a standalone `json.loads` round-trip before the write; better, give fleet-streamjson.sh a first-class `relay <worker> --message <text>` or `--message-file` subcommand that owns the framing, since `steer` is advertised in the backend capability contract but ships no command, which is precisely why towers hand-write stream-json into the fifo in the first place. Recovery worked cleanly via `fleet-streamjson.sh recover <worker>`, which resumed both sessions with context intact.
