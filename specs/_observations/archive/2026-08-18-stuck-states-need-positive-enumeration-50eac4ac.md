- 2026-08-18 [planwright] A stuck-detector MUST enumerate its stuck states positively, because every stuck state looks like silence. Observed 2026-08-13: a hand-rolled monitor that sampled only the LAST pane line reported eleven consecutive identical heartbeats for a worker that was frozen at a permission dialog, and read as healthy throughout -- the last line was stable precisely BECAUSE the worker was stuck. Detecting the blocked state required matching the permission-dialog signature explicitly; no amount of sampling the same impoverished signal would have produced it. Generalizes to the whole fleet monitoring surface: liveness-by-absence-of-change is not a detector, it is a coin flip whose bias depends on what you happen to sample. The four states an operator actually needs separated -- working / waiting-on-a-human / finished-but-unreaped / dead -- each need their OWN positive script-readable signal, and the third is the one nothing models today (obs b63a8778: the fleet oracle has no notion of alive-but-finished, which let two completed workers sit unread for two hours in the same session that leaked ~95 worker-hours). Related: obs cc13d432, where status reported completed=success while work was stranded, is the same failure from the opposite direction -- a positive-looking signal that encodes nothing about whether the work actually landed.
