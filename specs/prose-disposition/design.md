## Decision log

### D-1: Altitude — doctrine first, the guard as a core capability, the cleanup as local work  (N)

**Decision:** The deliverable is doctrine-led. The three composing rules are
amended in their own docs and a new rule doc states what a comment is for;
the comment-block budget lands in core as a capability (a guard with
overlay-tunable knobs and a suppression list, default-preserving through its
transitional baseline); the thresholds planwright picks and the cleanup of
planwright's own scripts are local values and local work. Nothing here is a
planwright-only script that carries doctrine in its header.

**Alternatives considered:**
- Mechanism only: a size guard plus a deep clean, the original shape of the
  issue. Rejected because: the measurement falsified its premises. A size
  guard caps surface area and a deep clean deletes rationale (132 of the 138
  large blocks cite a spec, 109 carry rationale, 2 of 2,526 duplicate spec
  prose); neither touches why prose is expensive, which is the disposition
  machinery every finding enters.
- Cleanup first, doctrine later. Rejected because: under today's rules a
  comprehensive cleanup is roughly a thousand Needs-sign-off entries, one
  commit each, generated by the very rules this bundle amends.
- Doctrine only, no guard and no cleanup. Rejected because: the 250-line
  headers regrow with every task, the 2026-09-03 measurement stays a one-off
  nobody can rerun, and the operator's requirement is a confirmed clean
  corpus.

**Chosen because:** the altitude trigger fired on pinned seed claims ("the
proposal targets the wrong layer", "three doctrine rules compose into the
actual multiplier"), and the autopilot reflex's right-altitude step puts
rules about how findings are judged in doctrine, the ability to bound a
surface in a core capability, and one repo's numbers and cleanup in local
value and local work.

### D-2: The Documentation lens gets a defect class  (N)

**Decision:** The code lens set's Documentation lens flags four things and
nothing else: prose the change falsifies or leaves stale, documentation
missing for behaviour or a contract the change introduces, a violation
a shipped documentation guard reports, and prose two readers would act
differently on (an interpretation fork, the code set's counterpart of the
spec set's ambiguity lens). A cross-set sentence in the
artifact-lenses doc states that merely improvable prose is not a finding in
any lens set, and every documentation finding names its class. The
coverage-table row carries the class per finding.

**Alternatives considered:**
- Drop the Documentation lens. Rejected because: the defect class is real.
  The release-proposal workflow header promised a guarantee its code could
  not deliver (issue #380); a fleet doc claimed the ledger records what a
  worker said when the text never enters it. Those are exactly the findings
  a reviewer needs.
- Keep the lens unscoped and rely on proportionality or the refactor
  instinct's review-mode bar. Rejected because: the refactor instinct's bar
  covers structure, not documentation, and a scoping applied by feel is the
  silent scoping the rigor docs forbid.
- Make the lens fire only on guard-reported violations. Rejected because:
  falsified prose has no guard; the contradiction between a header and its
  code is found by reading.

**Chosen because:** naming the defect class keeps the finding that protects
readers (a claim the code contradicts) and removes the finding that only
costs them (a phrasing that could be sharper), without touching the
no-pruning discipline: the coverage row still emits, now with the class
that shows whether a pass stayed inside its scope.
*(Amended at kickoff walkthrough 2026-09-04: interpretation-fork class
added, so REQ-A1.1's classes cover every conjunct of REQ-A1.2's test.)*

### D-3: Prose findings ride the meta-spec's amendment axis  (N)

**Decision:** A prose-only finding is classed expression-only or
meaning-class, the axis the meta-spec already defines for bundle
amendments. Expression-only prose is Auto-applicable: its grounding is
either a prose-guard rule or a recorded normative-preservation check (the
normative statements of the passage listed before and after, identical),
its fix is mechanical by construction, and no behaviour changes because no
rule changed. A normative statement is any obligation, permission, or
prohibition however worded, plus thresholds, enumerated values, and
interface facts; the categorization doc keeps a word list (RFC keywords
plus the plain imperatives) as the check's search aid and grows it on
evidence, and a future normative-diff guard is the mechanism that list
seeds (a Deferred entry in `tasks.md`). Meaning-class prose to a pre-existing surface keeps the
Needs-sign-off route, and on a signed bundle is refused to the kickoff
re-walkthrough. "External contract", for prose, means a normative rule a
reader outside the PR relies on.

**Alternatives considered:**
- Mint a fifth bucket for prose. Rejected because: the buckets are an audit
  vocabulary fixed at four by the bootstrap bundle; a fifth ripples through
  every table, checklist, and the unattended tower's policy mapping, for a
  distinction the existing axis already draws.
- Give Agent-resolvable a non-code evidence form, the alternative the Task 1
  observation offered. Rejected because: that bucket's predicate is a
  failing-then-passing test plus brief alignment, and prose has neither;
  loosening its evidence row for prose weakens the bucket for code.
- Treat all prose as Auto-applicable. Rejected because: turning a MAY into a
  MUST changes what a conforming reader must do; that is a contract change
  and a human should see it listed.

**Chosen because:** the axis exists, has a human-classified precedent at
every sign-off, and is what the meta-spec's writer obligations already key
on; reusing it costs one paragraph and no new vocabulary.
*(Amended at kickoff walkthrough 2026-09-04: normative statement defined by
meaning rather than by the RFC keywords alone, since planwright's doctrine
states most rules as plain imperatives; a word list is the search aid.)*

### D-4: A prose surface the PR introduces carries no external contract until it merges  (N)

**Decision:** When the file being edited is absent from the PR's base, its
prose is internal until merge: a documentation, doctrine, or skill file
whole, and the comments of a new code file. Every review-loop edit to that
prose is applied and batched with the iteration's action commit and reviewed
as part of the new content in the PR diff, with no checklist entry. The code
of a new file keeps its existing routes.

**Alternatives considered:**
- Route by content regardless of the file's age. Rejected because: all 30
  measured items edited a doctrine doc the same PR created, so no reader
  outside the PR could have relied on any wording being changed; 30 sign-off
  decisions guarded a contract nobody yet held.
- Extend the rule to code in new files. Rejected because: a new script's
  flags and exit codes are a contract choice the moment the PR merges, and a
  reviewer is better served by a checklist line pointing at them.

**Chosen because:** an external contract needs an external reader, and before
merge there is none; the PR diff is where a new file is reviewed whole.

### D-5: Meaning-class prose batches per iteration with a manifest  (N)

**Decision:** Needs-sign-off fixes that edit only prose land in one commit
per loop iteration. The commit body carries a manifest, one line per fix
(file, the rule before, the rule after), and the pending-sign-off marker is
stamped once, in whatever carrier gate-wiring defines at the time. The
checklist shows one entry with the manifest lines as sub-items and the
batch's revert command; the audit table keeps one row per finding sharing
the commit and checklist id. Any Needs-sign-off fix that changes code
behaviour stays one commit per finding.

**Alternatives considered:**
- Batch per touched file. Rejected because: the measured case was one
  doctrine doc, where per-file and per-iteration coincide; in the multi-file
  case per-file adds entries without adding revert precision a reviewer has
  asked for.
- No batching; rely on D-3 and D-4 alone. Rejected because: the
  reclassification covers about one third of the measured queue and the
  new-file rule covers a new doc's first PR; a meaning-class reword of an
  existing doctrine doc would still cost a commit and a decision each.

**Chosen because:** the one-commit-per-finding guarantee exists so a single
`git revert` undoes one item, and that is worth its cost for behaviour,
where a partial revert can break things, not for wording, where a manifest
makes the batch both reviewable and hand-revertable. Sequencing risk: the
trailer work in issue #384 rewrites the same commit-discipline and checklist
sections to move the marker; whichever change lands second re-reads the other's
text before editing, and this bundle names the carrier abstractly so the
order does not matter to its rule.

### D-6: Skills cite the amended sections; stragglers are swept by surface pattern  (N)

**Decision:** `/self-review`, `/polish`, and `/execute-task`'s convergence
prose cite the amended doctrine sections and restate at most the one-line
gist a step needs. Landing the amendments includes a grep sweep of `skills/`,
`doctrine/`, and `docs/` for the superseded wording, fixing every straggler
in the same change. A warn-threshold crossing on gate-wiring is answered by
the diet rung, never a raise.

**Alternatives considered:**
- Rely on the doctrine-manifest guard. Rejected because: it verifies that a
  skill cites a doc, not that the skill's restatement matches the doc; the
  2026-08-27 straggler observation is exactly that gap.
- Build the restatement detector first. Rejected because: its own
  observation names the false-positive risk on quoted grammar and fixed
  vocabulary, and it is out of this bundle's scope.

**Chosen because:** the validation-rigor doc already prescribes searching the
affected files for the rule's surface patterns before declaring alignment;
this applies the rule to its own change.

### D-7: A new rule doc, comment-hygiene, rather than a section in an existing one  (N)

**Decision:** `doctrine/comment-hygiene.md` holds the comment rule, the
provenance rule and its replacement link, the disposition taxonomy, and the
budget model. It is enrolled in the doctrine index and cited by the guard
header. No skill front-loads it: the Documentation lens states its own
defect class in one line inside discovery-rigor, so its consumers need no
new manifest entry.

**Alternatives considered:**
- A section in `instruction-hygiene.md`. Rejected because: that doc sits
  near its warn threshold and is run-start for several skills, so a section
  charges every one of them at start-load; and its subject is instruction
  files the harness injects, not source comments an agent reads on open.
- A section in `refactor-instinct.md`. Rejected because: that doc sets a
  review bar for structure; this is authoring law for a surface.
- No doc; the guard header carries the argument, as the instruction guard's
  header does today. Rejected because: doctrine buried in a script is
  invisible, and the header would exceed the budget it enforces, the irony
  the primary observation already records.

**Chosen because:** a rule doc is where planwright puts law a mechanism
enforces, and a small doc with no run-start consumer costs no skill any
budget.

### D-8: The five-reason taxonomy decides where surviving comment text goes  (N)

**Decision:** Existing comment text is dispositioned by why it survives the
restatement pass. The why of this code (a workaround, an ordering
constraint, a rejected alternative) stays and moves beside the code it
explains. An own-surface contract (usage, flags, exit codes) stays as the
file's bounded usage section. A cross-file protocol (store precedence,
last-write-wins, a fence's semantics) moves to the doctrine doc or a design
page that owns it, with a one-line pointer left behind. Restatement of what
the code does and history (task numbers, risk rows, review notes) are
deleted. A warning against a plausible wrong edit stays beside the code it
guards. An `exempt` entry is reserved for an own-surface section that
remains over the error threshold because the taxonomy offers it no split
and no other home, and for a file where the heredoc limit misfires (D-10).

**Alternatives considered:**
- One destination for all survivors (a design page per script family).
  Rejected because: the operator's call was that the destination depends on
  why the text survived; a why-of-this-code moved away from its code is the
  drift this bundle exists to stop.
- Exempt every large header. Rejected because: the header keeps loading into
  an agent's context on every open, which is the cost being paid.
- Amend the owning spec bundle as the default destination. Rejected because:
  each such edit is meaning-class on a signed bundle and needs a kickoff
  re-walkthrough, across many bundles; kept only as the destination when the
  protocol's normative home already is a bundle.

**Chosen because:** splitting a monolithic header into small local comments
brings most files under budget without losing a word, and the remaining
text has a home that matches its reason.

### D-9: Budget model — largest contiguous block per file, in lines, two suppression forms  (N)

**Decision:** The guard measures the largest contiguous run of comment lines
per file and compares it to `comment_block_warn` and `comment_block_error`
(lines, boundary-inclusive, shipped at 12 and 25). The suppression list has
two forms, permanent `exempt` and transitional `pending-cleanup`, each with a
recorded reason. Knobs are core, overlay-tunable, documented in the options
reference, fail-loud when missing or non-numeric. Untrusted-input posture
throughout.

**Alternatives considered:**
- Total comment volume or comment-to-code ratio. Rejected because: the block
  is the unit that costs review attention and context; many small comments
  beside the code they explain is the goal, not a violation.
- Words, as the instruction-budget guard measures. Rejected because: words
  defeat reflow gaming for instruction files, but a comment block's shape is
  visible in the file, and the audit reports words per block informationally
  so a reflowed block stands out; lines are what the issue and the operator
  measured and reason in.
- Higher defaults. Rejected because: 25 lines is already a screen of prose
  before the first line of code.
- The instruction budget's four suppression forms. Rejected because: there
  are no headroom floors here to declare exceptions against, and a raise is
  simply an overlay value; two forms suffice.

**Chosen because:** the model mirrors the guard planwright already trusts
where the surfaces are alike and departs only where comments differ from
instruction files.

### D-10: Surface — every tracked `#`-commented file under scripts, tests, githooks, hooks, config, plus root tool config  (N)

**Decision:** Shell files under `scripts/`, `tests/` (including its sourced
library), `githooks/`, and `hooks/`, plus YAML under `config/`, plus the
root-level tool configuration (`lefthook.yml`, `mise.toml`) and the workflow
YAML under `.github/workflows/`. The
comment-line definition is stated once in the guard's usage text with its
known limit: a heredoc body line beginning with `#` counts as a comment
line, and a file where that misfires takes an `exempt` entry naming it.

**Alternatives considered:**
- Scripts only. Rejected because: the config-comment-drift observation was
  consumed into this bundle, and `defaults.yml` carries five comment lines
  per code line with paragraphs the options reference already guards.
- Every text file, including markdown and JSON. Rejected because: markdown
  is the instruction-hygiene budget's surface, and JSON has no comments (its
  `_about` strings are a separate observation, out of scope).

**Chosen because:** `#` is the one comment syntax across these files, so one
definition covers them all, and the limit is named rather than hidden.
*(Amended at kickoff walkthrough 2026-09-04: root-level tool configuration
and workflow YAML added; same syntax, and the workflow-header drift cited in
Sources is the defect class the guard exists for.)*

### D-11: The guard lands green, with a generated transitional baseline  (N)

**Decision:** The guard lands with `pending-cleanup` entries generated from
its own audit for every file the error threshold catches, each naming the
cleanup task that removes it; the aggregate check stays green from day one,
the cleanup tasks delete entries as they land, and planwright's own task
passes `--closeout` once the cleanup completes.

**Alternatives considered:**
- Land warn-only until the cleanup finishes. Rejected because: a warning
  nobody must clear is how 250-line headers grew in the first place.
- Land the guard after the cleanup. Rejected because: the cleanup's
  verification is the guard's audit, so the guard has to exist first.

**Chosen because:** the prompt-hygiene retrofit followed exactly this shape
(transitional allowances, closeout), and it worked.

### D-12: Verification is three-legged  (N)

**Decision:** Each cleanup PR proves itself three ways. Reproducible
measurement: the guard's `--audit` is the inventory, run before and after,
figures in the PR body. Mechanical code invariance: `--code-invariant`
compares the code lines (non-blank, non-comment) of every touched surface
file against the merge-base and fails on any difference. Independent
reading: a second pass from a fresh session or a non-Anthropic review
backend confirms every removed line is recoverable from the code, the
history, or its named destination, and every surviving block names its
taxonomy reason (in full for Phase B; over a named sample for Phase A);
disagreements are resolved by the author in the PR, and the operator's
merge is the binding approval.

**Alternatives considered:**
- The author's own verification. Rejected because: the operator requires the
  result confirmed, and the author reviewing the author's deletions is the
  independence collapse the comprehension doctrine warns about.
- A full operator re-read. Rejected because: 8,729 lines in the large blocks
  alone is the burden this bundle is meant to remove, not relocate.
- Mechanical checks only. Rejected because: no script can judge whether a
  surviving why earns its place.

**Chosen because:** the first two legs are cheap and exact, and the third is
scoped to what only a reader can judge.
*(Amended at kickoff walkthrough 2026-09-04: the code-invariance leg is
enforced by a PR-only CI step on PRs declaring a `comments` title scope,
using the base-ref plumbing and title lint the workflow already has, so a
cheap exact leg is a gate rather than an author attestation; the worker
still records the result in the PR body for the second reader.)*

### D-13: Ordering — doctrine, skills, guard, Phase A, Phase B, closeout  (N)

**Decision:** The doctrine amendments and the skill instantiation merge
first; the rule doc and the guard follow; Phase A (evidence-free blocks by
rule) runs next; Phase B (large evidenced headers by reading) is split by
script family for parallel workers after Phase A; a closeout task wires
`--closeout` and records the final figures. The cleanup tasks carry
explicit dependency edges on the doctrine tasks.

**Alternatives considered:**
- Guard first. Rejected because: the guard cites a doctrine home that does
  not exist yet, and a guard that fires before the disposition fix spawns
  sign-off entries under the old rules.
- Cleanup in parallel with the doctrine work. Rejected because: the
  ordering is the load-bearing claim of the seed; roughly a thousand
  sign-off entries is the measured cost of getting it wrong.

**Chosen because:** every later step is verified by an earlier one: the
skills apply the doctrine, the guard measures the cleanup, the closeout
proves the guard.

### D-14: Provenance leaves source; the deliverables gap closes at its source  (N)

**Decision:** No spec, requirement, decision, or task identifier, PR link,
or review note remains in a comment. The script-to-spec link lives in the
commit's task trailer and the owning bundle's task deliverables. The
scripts REQ-E1.5's link test finds unlinked (28 at the 2026-09-03
measurement) are named in their owning bundle's deliverables as
expression-only amendments (changelog entry plus the machine
self-re-anchor), riding the Phase B PR for their script family; the set is
recomputed, never carried.
*(Amended at kickoff walkthrough 2026-09-04: the fixed 28-script list
replaced by REQ-E1.5's recomputed test, per the meta-spec's cite-the-source
rule.)*

**Alternatives considered:**
- Keep one owning pointer per file. Rejected because: it is one provenance
  line per script that the comment rule says should not be there, and
  102 of 130 scripts already have the link elsewhere.
- Strip everything and accept the gap. Rejected because: 28 scripts would be
  reachable only through `git log` on the file, and the meta-spec says
  deliverables live in the bundle.

**Chosen because:** the measured redundancy is four in five, and the gap is a
bundle defect with a sanctioned expression-only fix, not a reason to keep
citations in code.
